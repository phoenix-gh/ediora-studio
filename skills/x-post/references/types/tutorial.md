# types/tutorial.md：教程帖

**先读 skeleton.md 和 voice-MK.md，再读本文件。**

教程帖 = 推荐一个工具/方法/经验，告诉读者它能解决什么问题、怎么用、注意什么。

---

## 取材规则

### 适合做教程帖的素材

- **你亲自用过的工具/方法**（没用过别写）
- **能在 1-3 段内说清核心机制的东西**（机制太复杂的拆 thread 或写长文）
- **和读者的日常痛点相关**（小众工具也行，但要明确它解决谁的问题）

### 不适合做教程帖的素材

- 你只听说过没用过的东西
- 需要长篇 step-by-step 的安装指南（X 不适合，写博客更好）
- 营销味重的"5 个工具推荐合集"（除非每个都真的用过）

---

## 教程帖的标准骨架

```
[钩子句]：试用下来 / 推荐一个 / 有个工具值得一说 → [工具名] [评价词]。

[1-2 段]：它是什么？解决什么问题？跟主流方案的差异在哪？
（这里很容易写成产品介绍，注意要从"它能帮你做什么"切入，不是"它是什么"。）

[1 段]：核心机制 / 用法关键点。
（如果有反直觉的细节，重点讲这个。）

[1 段]：注意事项 / 局限。
（这一段是教程帖的"诚信税"，不写就显得像软文。）

[结尾]：升维 / 彩蛋 / 提问 三选一。
```

---

## 钩子模板（教程类）

### 模板 1：试用 + 表态
```
试用下来 [工具] 不错，推荐下。它 [一句话讲清核心特征]。
```
适合：你有明确推荐意愿，工具有清晰卖点。

### 模板 2：解决了一个老问题
```
[一个让人头疼的老问题] 终于有个不错的解法：[工具名]。
```
适合：工具切中明确痛点。

### 模板 3：反直觉的工具
```
[工具] 跟你想的不一样。它不是 [常见认知]，而是 [实际机制]。
```
适合：工具的机制本身有反直觉点。

### 模板 4：从对比切入
```
最近在 [A] 和 [B] 之间反复横跳，最后选了 [B]，因为 [一句话理由]。
```
适合：选型类教程，决策过程本身有信息价值。

### 模板 5：踩坑提醒
```
[工具] 用了三个月，最大的教训是 [反直觉的发现]。
```
适合：经验积累型，避坑价值明确。

## 教程帖最容易翻车的点

1. **写成产品介绍页**：堆功能、堆"特性"、用产品官网的话术
   → 救：每段都问"这一段读者能拿走什么？"

2. **没有亲身体验感**：通篇都在说"它能"、"它支持"，没有"我用下来"
   → 救：至少要有 1-2 处"我"或具体使用场景

3. **缺少"注意事项"段**：全是好话
   → 救：必须有一段写局限、踩坑、不适合的场景

4. **结尾平淡**：写到注意事项就结束了
   → 救：必须按 skeleton.md 的三种结尾选一个

## 真实案例参考（宝玉的 CodexPotter）

```
试用下来 CodexPotter 不错，推荐下。它不是基于 Codex 插件机制，它本身是一个 cli，
然后会后台启动 codex cli，把指令传给 codex，同步显示 codex cli 结果。

CodexPotter 先把想要的结果写进一个 MAIN.md 文件，然后工具在后台不停地启动新的
Codex 会话，每一轮都用全新、干净的上下文，对照 MAIN.md 检查代码、修正、再检查、
再修正，直到结果跟你写的一致才停。

默认最多是 6 轮，但是你可以通过配置修改数字。

使用上需要注意，CodexPotter 适合目标明确的任务，比如"按照这个设计文档实现订阅
系统"，不适合需要来回讨论的交互式开发。它是个任务执行器，不是聊天伙伴。

顺便说一下：Ralph 这个名字的来源是《辛普森一家》那个爱重复同一句话的小孩
Ralph Wiggum pattern。
```

**拆解**：
- 钩子：模板 1（试用 + 表态）
- 1 段机制（"不是 X，而是 Y"的反直觉切入）
- 1 段核心用法
- 1 段配置细节（短）
- 1 段使用边界（"适合 / 不适合"）
- 结尾：冷知识彩蛋（Ralph 的来源）

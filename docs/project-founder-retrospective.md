# 从 WeMedia Studio 到 Ediora：一个内容工作台的创始人复盘

#### 2026 年 5 月 4 日—2026 年 8 月 13 日

这不是一篇版本发布说明，也不是简单的功能清单。

这是我站在项目创始人的角度，对 WeMedia Studio——后来逐渐品牌化为 Ediora、述策——从开始到现在的一次完整复盘。

我想讲清楚的，不只是我们做了什么，还包括：

- 为什么一开始会走向一个很重的 Agent 架构；
- 为什么后来决定放弃 Hermes；
- 为什么明明只是“做一个内容工具”，最后却长出了采集系统、素材库、技能运行时、任务队列、视频生产、数字人和 Chrome 插件；
- 哪些功能真正落地了，哪些只是讨论过；
- 哪些坑是技术问题，哪些其实是产品边界问题；
- 以及，一个个人开发者或小团队，如何从这些经历里得到一些可以复用的经验。

---

## 一、最初想做的，不是一个 AI 写作工具

项目仓库可以追溯到 2026 年 5 月 4 日的初始提交。

但如果只把它理解成“AI 自动写文章”，从一开始就理解错了。

我真正想解决的问题是：

> 信息每天都在产生，但从信息到内容之间，存在一条很长、很碎、很依赖人工的链路。

我需要不断面对这些事情：

- 关注哪些账号和信息源；
- 哪些内容值得收藏；
- 哪些内容只是噪音；
- 一个热点能不能变成选题；
- 这个选题适合写成长文、短文还是评论；
- 应该使用什么账号画像和写作风格；
- 是否需要封面、插图或视频；
- 最后如何发布到公众号、X、博客等平台。

所以 WeMedia Studio 从一开始就不是一个单点工具，而是一个内容生产工作台：

> 采集 → 筛选 → 分析 → 选题 → 创作 → 素材 → 视频 → 发布辅助

这个方向后来一直没有改变。改变的是我们对每个环节应该由谁负责、数据应该如何流转、自动化应该走到哪一步。

---

## 二、第一阶段：先把所有有用的能力都做出来

### 1. 从 X 采集开始

最早的能力集中在 X 内容采集。

项目很快支持了：

- X 长文章和 Article 内容采集；
- 时间线监控；
- 关键词搜索；
- 热度过滤；
- 原创帖和回复区分；
- 文章、图片、作者信息保存；
- 采集后的灵感和草稿管理。

最初使用过 Twitter API、网页抓取和一些中间方案，后来逐渐转向 feedgrab。

这个阶段最明显的特点是：我们一直在和外部平台的不确定性作斗争。

X 的数据接口、搜索语义、Cookie、限流、响应格式和排序规则，都不是稳定的内部函数。一次看似简单的“拉取帖子”，实际包含了：

- 认证是否有效；
- Cookie 是否过期；
- 当前账号是否被限流；
- 搜索语法是否被平台接受；
- 返回结果是否包含回复；
- 分页游标是否失效；
- 采集结果是否重复；
- 内容是否已经被其他订阅处理。

这让我很早意识到：

> 内容采集不是调用一个 API，而是维护一套持续变化的外部系统适配层。

后来项目又陆续接入了：

- RSS；
- YouTube；
- Reddit；
- 掘金；
- 36 氪；
- V2EX；
- 公众号；
- GitHub Release；
- 本地文件和外部文章。

到这里，项目已经不再是一个 X 工具，而开始变成一个内容信息基础设施。

### 2. 从 SQLite 逐渐转向 PostgreSQL

随着数据模型开始变复杂，PostgreSQL 变得越来越必要。

项目中出现了越来越多的实体：

- 订阅；
- 采集帖子；
- 内容资产；
- 草稿；
- 写作方案；
- 发布账号；
- 采集规则；
- 任务；
- 响应分析；
- 素材；
- 图片、音频和视频资产。

数据库不再只是存几个配置，而是开始保存一个内容系统的历史。

这一步带来的收益很明显：

- 可以保存长期状态；
- 可以追踪任务；
- 可以做幂等处理；
- 可以保留失败记录；
- 可以对历史数据进行迁移；
- 可以让 worker 重启后继续恢复工作。

但它也埋下了一个长期问题：

> 数据模型增长得比产品边界更快。

当每个新功能都添加一批表、字段、路由和页面时，系统很容易变成“什么都能存，但没人知道哪些数据真正重要”。

## 三、第二阶段：从内容采集扩展到完整创作流水线

5 月底到 6 月，项目进入了功能快速扩张期。

这段时间，我们做了很多事情。

### 1. 选题和写作方案

项目先后加入了：

- 趋势主题生成；
- 主题分析；
- 主题标签；
- 写作计划；
- 文章类型；
- 封面风格；
- 插图风格；
- 创作目标；
- 长文、短文、故事、评论、教程等不同写作流派。

后来我们又把 ContentTopic 改成了 WritingPlan。

这背后其实是一个重要变化：

一开始，我们把内容理解成“一个主题”。

后来发现，一个主题本身还不够。真正决定文章结果的，是：

- 为什么写；
- 写给谁；
- 采用什么角度；
- 采用什么内容类型；
- 需要什么语气；
- 需要什么视觉风格；
- 发布到哪些平台。

也就是说，内容创作的核心不是一个 prompt，而是一份可持续修改的创作方案。

### 2. 参考文案库

我们一度有“金句库”、参考文案、帖子收藏等多个概念。

后来把它们逐渐合并成统一的“参考文案库”。

这个过程很有代表性。

早期的思路是：

> 采集到好的内容，就直接交给 LLM 判断和分类。

后来发现这样做成本高、难以重试，也很难知道哪些内容没有被处理。

于是采集清洗流程被拆成了两层：

第一层只负责：

- 采集原始内容；
- 去重；
- 记录来源；
- 保存基础数据；
- 标记未处理状态。

第二层再负责：

- 分类；
- 热度评分；
- 近重复检测；
- 回复筛选；
- 主题提炼；
- 人工确认。

这是一条非常重要的经验：

> 不要让采集层和智能处理层绑死在一起。

采集应该尽量稳定，LLM 清洗可以异步、可重试、可替换。

如果采集和 LLM 绑定在一个请求里，模型失败会影响采集；如果模型规则改变，又很难重新处理历史原始数据。

### 3. 从 GitHub Release 自动生成草稿

项目后来加入了 GitHub Release 的自动写稿。

它让内容工作台第一次明显具备了“持续产出”的感觉：

- 采集新的 Release；
- 判断是否值得写；
- 生成文章；
- 可选生成封面；
- 保存到草稿箱；
- 等待人工编辑和发布。

但是也暴露了一个问题：

> 自动生成并不等于自动发布。

后来这个原则成为整个项目的安全边界。

生成内容可以自动化，发布必须是明确动作。

### 4. 公众号、博客和 X 发布辅助

项目陆续接入了：

- 公众号草稿箱；
- 公众号图片上传；
- Markdown 转公众号格式；
- 博客发布；
- X 长文复制；
- 发布账号画像；
- 发布前预览；
- 发布账号配置。

当时我们还做过“发布表现”记录和历史分析，希望让系统根据过去的发布数据优化后续选题。

后来这个方向被重新审视，最终删除了独立的 publication record 管理层，但保留了真正的发布能力。

这是一次很典型的产品收缩：

> 发布记录、发布分析和发布动作，并不是同一个需求。

用户需要的是：

- 把草稿发到公众号；
- 把文章复制到 X；
- 把内容提交到博客。

不一定需要在系统里再维护一套复杂的“已发布内容管理后台”。

这次删除让我认识到：

> 不是所有可以建模的东西，都值得成为产品的一部分。

## 四、最大的转折：为什么决定放弃 Hermes

项目中最重的一段历史，就是 Hermes。

Hermes 一开始很有吸引力。

它提供了：

- Agent profile；
- SOUL；
- 工具和技能；
- MCP；
- Kanban 任务；
- Session；
- Retro；
- 多 Agent 协作；
- 网页终端；
- 任务恢复。

对于“让几个 Agent 自己协作完成内容生产”这个想法来说，它很自然。

我们曾经把内容流程设计成：

- scout；
- editor；
- writer；
- illustrator；
- critic；
- planner。

但系统越做越大，我逐渐意识到：

> Hermes 解决的是一个比当前产品更大的问题。

它本质上是一个 Agent 运行平台，而我需要的是一个个人内容工作台。

这两者差别很大。

一个个人用户真正想要的是：

- 启动项目；
- 连接自己的数据源；
- 选择素材；
- 生成文章；
- 看见进度；
- 修改草稿；
- 生成图片；
- 再决定是否发布。

他不应该被迫理解：

- Agent profile；
- Kanban board；
- session resume；
- 终端复盘；
- Hermes home；
- 多个常驻角色；
- 额外的本地 Agent 运行环境。

所以在 7 月 22 日，我们明确了新的方向：

> 做一个开源、无登录、单用户、可自托管的版本；未来再保留 SaaS 演进空间。

新架构大致是：

~~~text
浏览器
  ↓
Next.js：产品界面、AI SDK、流式状态
  ↓
Python API：采集、领域逻辑、素材、发布
  ↓
PostgreSQL：业务数据和任务状态
  ↓
Redis + Worker：异步执行
~~~

Python 不再承担 Agent runtime，而是负责：

- 内容采集；
- 领域 API；
- 数据库；
- 素材管理；
- 发布适配；
- 长时间运行的外部集成。

Next.js 和 Vercel AI SDK 负责：

- 用户交互；
- AI 编排；
- 工具调用；
- 实时进度；
- 任务详情。

### 真正重要的，是 durable job

迁移的核心并不是把 Hermes 替换成另一个聊天 SDK。

真正的核心是把任务从“对话上下文中的一次执行”，变成持久化 job：

~~~text
queued → running → succeeded
                 → failed
                 → cancelled
~~~

每一个 job 都有：

- step；
- attempt；
- input；
- output；
- error；
- event；
- retry；
- cancellation；
- idempotency key。

这样做以后，一个失败的封面生成不应该导致整篇文章重新生成；worker 重启也不应该让任务历史消失；用户可以只重试失败的步骤。

这个架构带来的最大收益是：它让系统从“Agent 运行一次”变成了“产品有一份可解释的执行记录”。

### 但我们后来发现：问题不是 Agent，而是失控的 Agent

有意思的是，放弃 Hermes 之后，Agent 并没有完全消失。

到了 8 月，项目又逐渐建立了：

- 技能注册；
- 技能启用；
- 参考资料加载；
- 通用技能运行时；
- 技能执行；
- 输出验证；
- 失败恢复；
- 每日创作 Agent；
- 工具审计；
- 执行证据。

这说明最初的判断还可以更精确一点：

> 我们不是不要 Agent，而是不要一个过重、无边界、不可审计的 Agent 平台。

真正适合产品的 Agent，应该是：

- 有明确目标；
- 有有限工具；
- 有严格 schema；
- 有可验证输出；
- 有持久执行记录；
- 有清晰的失败边界；
- 有人工确认点。

这也是最近检查 job #1552 时最重要的体会。

一个 job 生成了文字，并不代表它完成了运行时 Skill 要求。

我们必须区分：

- Skill 是否真正加载；
- Skill reference 是否被读取；
- 工具是否按要求调用；
- 写入是否有真实证据；
- 输出内容是否符合 Skill；
- 任务是否只是“看起来完成了”。

这标志着项目从“让模型生成内容”，进入了“让运行过程可审计”的阶段。

## 五、基础设施最容易骗人：Redis、Worker 和本地环境

迁移到 AI SDK 和 durable jobs 后，我们遇到过一个很典型的问题。

本地调用：

~~~text
POST /api/jobs
~~~

返回 500。

一开始很容易怀疑：

- 模型 API；
- prompt；
- 图片接口；
- worker；
- job schema。

但最后发现，真正的错误是：

~~~text
redis.exceptions.ConnectionError:
Error -3 connecting to redis:6379
Temporary failure in name resolution
~~~

因为 Docker Compose 中使用的是：

~~~text
redis://redis:6379/0
~~~

而本机运行时应该使用：

~~~text
redis://127.0.0.1:6379/0
~~~

这件事看起来很小，却让我记住了一条非常重要的排错原则：

> 不要只测试 HTTP 请求是否成功，要沿着完整链路验证。

一个内容任务至少要检查：

1. HTTP 是否创建 job；
2. Redis 是否成功入队；
3. Worker 是否消费；
4. 模型是否调用；
5. 资产是否上传；
6. 数据库是否保存；
7. 前端是否能读取结果。

只验证第一步，不能说明任务真正成功。

我们还遇到过用不支持的 queue_probe 流程验证 worker 的情况。它可以证明队列被消费，却不能证明真实业务流程成功。

后来我们开始更严格地区分：

- 队列通了；
- worker 活着；
- 模型返回了；
- 业务结果可用。

这四件事不能混为一谈。

## 六、从聊天入口到内容操作系统

Hermes 迁移之后，Next.js 聊天入口变得越来越重要。

我们为聊天加入了：

- 全局工具注册；
- 上下文选择；
- 草稿上下文；
- Skill 上下文；
- Markdown 渲染；
- 图片预览；
- 工具调用活动；
- Session；
- 任务状态；
- 草稿确认；
- 资产调用。

但产品没有停留在“聊天机器人”。

聊天只是入口，最终结果必须落到系统里的真实对象：

- 一份草稿；
- 一个素材；
- 一个创作任务；
- 一个图片资产；
- 一个视频项目；
- 一个响应分析；
- 一个发布动作。

这也是我们后来坚持“写入必须有真实工具证据”的原因。

模型说“我已经保存了”，不算保存。

只有当：

- save_draft 真正成功；
- job 有对应 output；
- 数据库有记录；
- 前端能重新读取；

才算真正完成。

## 七、待响应工作台：不是 Todo，而是行动收件箱

X 和 YouTube 的内容分析后来被统一到“待响应”工作台。

它支持：

- 内容来源筛选；
- X 帖子和 YouTube 视频；
- 分析任务；
- 字幕；
- 账号适配；
- 评论建议；
- 引用转发建议；
- 长文扩展；
- 手动采纳；
- Telegram 通知；
- 创作输出。

但这里有一个产品边界必须说清楚：

> “待响应”不是通用 Todo。

它更像一个行动收件箱。

一个响应项目的生命周期是：

~~~text
ready → used / ignored
~~~

用户可以：

- 复制内容；
- 打开原文；
- 采纳创作；
- 稍后处理；
- 忽略。

但系统不会强行加入：

- 截止时间；
- 子任务；
- 项目；
- 标签体系；
- 通用提醒；
- 跨系统任务聚合。

因为如果没有具体需求，Todo 系统只会增加复杂度。

### X 自动发布的边界

X 响应助手设计成：

- 自动采集；
- 自动分析；
- 自动评分；
- 自动通知；
- 生成建议；

但不直接自动调用 X 的发布、回复、转发接口。

真正发布仍然由用户明确触发。

后面我们又做了 Chrome 发布插件，它可以辅助填入内容、调用 X 原生排程或进行浏览器端操作，但这仍然属于显式发布链路，而不是后台偷偷发布。

这是一条我认为非常重要的边界：

> 内容生成可以自动，公共发布必须可见、可控、可撤回。

## 八、数字人和文字视频：从文章走向多媒体

### 1. 数字人口播

数字人方向是后来确认的一个重要产品线。

最终确定的模型不是“点一下生成视频”，而是：

~~~text
数字人角色
  → 口播项目
  → 成片版本
  → 异步生成任务
~~~

角色包含：

- 正面照；
- 克隆声音；
- 默认环境。

项目包含：

- 标题；
- 当前脚本；
- 使用的角色；
- 可选环境。

每次生成都会冻结：

- 脚本；
- 角色；
- 声音；
- 环境；
- 模型参数。

这样历史视频不会因为用户后来修改角色而失真。

HeyGen 的代码链路已经加入了：

- API client；
- 角色；
- 口播项目；
- 脚本生成；
- durable job；
- 视频下载；
- 创作资产归档；
- 版本管理。

但真实 HeyGen 账号、套餐权限、音色克隆能力和大文件上传，仍然需要真实凭据下的冒烟测试。

尤其是音色克隆，不能因为接口代码存在，就宣称所有账号都能用。

### 2. 文字视频

文字视频是另一个复杂程度很高的方向。

它逐渐包含：

- 文稿；
- 语音生成；
- 本地 Whisper；
- 词级时间轴；
- 段落；
- 场景；
- Remotion 模板；
- 动效；
- 音频过渡；
- 预览；
- 渲染；
- 任务恢复；
- 资产保存。

它最困难的地方，不是把文字放到画布上，而是保持多个状态的一致：

- 音频时间轴；
- 字幕时间；
- 场景起止点；
- 词 ID；
- 模板参数；
- 用户手动调整；
- AI 自动分段；
- 重新生成；
- 渲染输出。

这段工作让我意识到：

> 多媒体编辑器本质上是一个状态一致性系统，而不是一个页面。

一个“看起来能播放”的 demo，不代表它支持真实编辑。

如果用户改了某个词的时间，系统必须知道：

- 哪个场景受影响；
- 哪个音频片段需要重算；
- 哪些输出已经过期；
- 是否需要重新渲染；
- 是否需要保存新的版本。

## 九、素材系统：最容易被低估的核心基础设施

项目中最容易被当作“附属功能”的，其实是素材。

后来我们建设了比较完整的创作资产体系：

- 文章资产；
- 图片；
- 音频；
- 视频；
- 封面；
- 插图；
- 外部图片导入；
- Markdown 编辑；
- 批量上传；
- 批量重命名；
- 批量删除；
- 目录；
- AI 生图资产；
- 数字人资产；
- 视频渲染输出。

最早的问题是，后端返回：

~~~text
/api/uploads/xxx.png
~~~

前端却直接在：

~~~text
http://localhost:3000
~~~

下加载它。

浏览器自然会把它当成前端自己的路径，而不是后端 API 的路径。

于是我们增加了统一的资源 URL 解析，让相对路径根据后端 API origin 转换成正确的绝对地址。

后来 Chrome 插件又遇到了一次更隐蔽的问题：

~~~text
Loading the image 'http://localhost:8000/api/uploads/...'
violates Content Security Policy:
img-src 'self' blob: data
~~~

这次图片地址本身没错，后端也能访问。

错的是：图片被插入到了 X 页面内部，而 X 页面的 CSP 不允许 localhost:8000。

最终解决方案是：

- Markdown renderer 先延迟加载本地图片；
- Service Worker 通过扩展权限请求图片；
- 转换成 data:image/...;base64,...；
- 再交给页面内的 img；
- 复制 Markdown 时仍保留原始图片 URL。

这件事给我的经验是：

> 素材 URL 不是一个字符串，而是跨服务、跨浏览器、跨安全边界的协议。

必须同时考虑：

- 后端 host；
- 前端 host；
- 浏览器 origin；
- CORS；
- CSP；
- 扩展权限；
- 复制后的目标环境；
- Docker 和本机地址差异。

## 十、真正让我改变做法的几个具体坑

### 1. CSS 修好了，但用户说“没任何效果”

草稿编辑器换行问题就是一个典型案例。

我们看到连续换行显示不明显，第一反应是加 CSS 间距。

测试通过了，页面看起来也似乎合理。

但用户实际反馈：

> 没任何效果。

进一步检查才发现：

- 数据库中的 \\n\\n 没丢；
- API 没丢；
- React state 没丢；
- 真正的问题在 Milkdown 对 Markdown 换行结构的解释。

后来尝试把空行转换成 <br /> 空段落，但又影响了单个换行的语义。

最终按用户要求完全回退特殊处理，保留编辑器原生行为。

这次经验非常直接：

> CSS 测试通过，不代表编辑器行为修好了。  
> Mock 测试通过，也不代表真实草稿被正确编辑。

### 2. Legacy 数据不能只修新流程

YouTube 逐字稿曾经有一个问题：

新提取的字幕会合并成句子，但旧记录仍然是 cue 级别。

如果只修提取流程，历史数据不会变化。

最后我们把兼容逻辑放在 API 读取边界：

~~~text
数据库旧数据
  → API 读取时标准化
  → 前端统一消费句子级结构
~~~

这比重新提取所有历史视频更安全，也更现实。

经验是：

> 当数据已经存在时，读边界往往比迁移所有历史数据更适合做兼容。

### 3. CSS 的 hidden 不一定真的隐藏

Chrome 插件空预览区一直显示：

~~~text
选择左侧草稿查看原文
~~~

虽然元素有：

~~~text
hidden=true
~~~

但组件 CSS 使用了：

~~~css
display: grid;
~~~

覆盖了浏览器默认的 [hidden] 行为。

最后不是只设置 hidden，而是同时设置：

~~~text
hidden=true
display:none
~~~

并通过真实 Chromium 检查元素高度是否变成 0。

### 4. 一个目录配置，最终变成两个生效规则

X 订阅目录路由问题中，用户把目录从“实用工具”改成“搞钱副业”。

但旧规则没有停用，于是两个规则同时生效。

结果就是同一个订阅可能把内容写进两个目录。

解决方式不是简单修改 UI，而是：

- 更新当前规则；
- 停用同一订阅的其他活动规则；
- 启动时迁移历史重复规则；
- 加测试保证单一生效规则。

这是一条典型的数据不变量：

> UI 看起来只有一个选择，数据库里也必须保证只有一个真正生效的状态。

### 5. 编辑器目录和左侧浏览目录被错误耦合

另一个资产系统问题是：

用户在文章编辑器里修改文章所属目录，左侧正在浏览的目录也跟着改变。

这是两个不同概念：

- 文章的归属目录；
- 当前浏览器的导航目录。

它们共享了状态更新函数，导致一个操作影响了另一个状态。

这类问题很难靠类型系统发现，因为每个变量都“合法”。

它需要的是更清晰的状态边界。

### 6. 任务安排和任务日志不是同一页面

我们曾经把“今日创作任务”同时当作：

- 定时规则；
- 运行日志；
- 任务执行面板。

后来重新拆开：

- /creation-rules 只管理规则；
- /jobs 负责执行日志和详情；
- 页面显示上次运行和下次运行；
- 时间由服务端根据规则时区计算。

这个调整看起来只是改名和移组件，实际上是一次产品语义修正：

> 一个页面应该服务一个主要任务，不要把配置、执行和审计混成一团。

## 十一、技能运行时：从“提示词”走向“执行合同”

项目后来引入了项目技能管理：

- Skill 目录；
- frontmatter；
- 项目级 source of truth；
- 启用和卸载；
- profile 兼容；
- reference；
- 自动加载；
- 技能执行；
- 输出验证；
- 失败恢复。

最初我们把 Skill 理解成一份“给模型看的说明”。

后来发现，这远远不够。

一个真正可用的 Skill 运行时必须回答：

- 什么时候加载；
- 加载哪些参考资料；
- 哪些工具可用；
- 哪些参数必填；
- 输出格式是什么；
- 哪些动作必须有证据；
- 失败后能否恢复；
- 是否允许重复写入；
- 如何判断输出符合要求。

例如，某些 Agent 工具没有提供目录参数，或者首次调用漏传目录，就会导致工具审计失败。

这不是模型“聪明不聪明”的问题，而是工具 schema 没有把业务前提表达清楚。

所以我们逐渐形成一个原则：

> 业务前提必须进入工具合同，而不能只写在自然语言 prompt 里。

最近对 job #1552 的检查，本质上也是在验证这件事：

- 输出内容是否真的符合运行时加载的 Skill；
- Skill 是否被实际读取；
- 任务是否完成了必要的保存和资产操作；
- 输出是否只是语言上“像完成了”，还是有真实执行证据。

这也是项目从“AI 生成”走向“AI 执行审计”的标志。

## 十二、项目目前真正是什么

截至 2026 年 8 月 13 日，项目已经不再是最初的单一仓库工具。

它现在有四个主要运行面：

1. FastAPI 后端；
2. Next.js Web 工作台；
3. Node 内容任务 Worker；
4. Chrome 发布和草稿插件。

主要能力包括：

- 多来源内容采集；
- X 订阅和搜索；
- Reddit；
- YouTube；
- 公众号；
- GitHub Release；
- 参考文案库；
- 内容分析；
- 写作方案；
- 草稿箱；
- 图片和多媒体资产；
- AI 生图；
- 内容任务；
- Skill 运行时；
- 每日创作规则；
- 统一待响应工作台；
- Telegram 通知；
- 公众号和博客发布辅助；
- X 浏览器发布辅助；
- YouTube 逐字稿；
- 中英双语字幕；
- 文字视频；
- 数字人口播；
- Chrome 浮动发布指挥台。

但功能多，不代表所有功能都处于同样成熟度。

### 已经比较明确的部分

- 单用户、无登录、自托管产品定位；
- 不依赖 Hermes 才能正常运行；
- Python 负责采集和业务 API；
- Next.js 和 AI SDK 负责产品入口与 AI 编排；
- PostgreSQL 保存业务和任务状态；
- Redis 只承担队列；
- Worker 执行长任务；
- 发布动作保持显式；
- 草稿和资产有明确存储边界；
- Skill 逐渐转向可验证运行时；
- X 响应工作台保持轻量行动收件箱。

### 仍然需要持续验证的部分

- 全部 Hermes 历史兼容路径是否已经清理干净；
- Docker Compose 在全新环境下是否能完整启动；
- X feedgrab 在真实 Cookie、代理和限流环境下的长期稳定性；
- YouTube Cookie、字幕、下载和本地 ASR 的真实运行；
- HeyGen 真实账号、套餐和音色克隆权限；
- 文字视频在真实 provider 下的完整生产和导出；
- 多媒体资产在不同浏览器和部署 origin 下的兼容性；
- 每日创作 Agent 在各种 Skill 和目录组合下的审计恢复；
- 本地桌面客户端是否真的值得从 Web 运行时演进出来。

Tauri、SQLite、本地 sidecar 的桌面客户端方案曾经讨论过，但目前仍然是建议，不应该被当作已经确定的架构。

## 十三、我认为这个项目最大的几个经验

### 经验一：先定义产品边界，再选择 Agent 架构

一开始我们先被“多 Agent 协作”吸引，后来才重新问：

> 用户到底要什么？

答案不是“看多个 Agent 工作”，而是“可靠地完成一件内容工作”。

所以架构应该服务于：

- 内容；
- 草稿；
- 素材；
- 任务；
- 发布；
- 恢复。

而不是服务于 Agent 本身。

### 经验二：AI SDK 解决生成，不解决系统可靠性

AI SDK 可以帮助我们：

- 调用模型；
- 流式输出；
- 调用工具；
- 组织多步生成。

但它不会自动解决：

- 任务持久化；
- 失败恢复；
- 重试；
- 幂等；
- 取消；
- 审计；
- worker 重启；
- 资产归档。

这些必须由产品架构自己完成。

### 经验三：把不变量写进数据库、schema 和测试

以下事情不能只依赖 UI：

- 一个订阅只能有一个有效目录规则；
- 一个 Skill 工具必须传目录；
- 一个创作输出必须关联正确的 response 和 analysis run；
- 一个草稿生成不能重复保存；
- 一个发布动作不能被生成 job 隐式触发；
- 一个历史角色修改不能影响旧视频版本。

业务规则越重要，就越不能只写在 prompt 和前端按钮里。

### 经验四：测试不是“绿了就结束”

这个项目里很多问题都说明：

- 单测通过，不代表真实浏览器通过；
- CSS 通过，不代表编辑器结构正确；
- worker 存活，不代表业务 job 成功；
- mock provider 通过，不代表真实 provider 可用；
- 静态搜索没有结果，不代表历史运行路径已经删除；
- 设计文档完成，不代表功能实现；
- commit 存在，不代表用户验收完成。

所以现在我更看重证据链：

~~~text
代码 → focused test → real workflow → browser/runtime → external provider
~~~

每一层证明的事情不同，不能互相替代。

### 经验五：要把“讨论过”和“完成了”严格分开

这个项目有大量设计和计划文档。

它们很有价值，因为它们记录了：

- 为什么做；
- 为什么不做；
- 边界是什么；
- 未来如何扩展；
- 哪些风险已经被看见。

但设计文档不是实现。

计划完成不是功能完成。

测试通过也不一定是生产完成。

现在回看，这种状态分类非常重要：

- 已提交并验证；
- 已实现但未完整验证；
- 只有设计；
- 只有讨论；
- 明确暂缓；
- 已删除；
- 当前工作区未提交。

如果不区分这些状态，项目报告很快就会变成愿望清单。

### 经验六：不要害怕删除功能

我们删除了：

- Hermes 依赖；
- Agent profile 的一部分；
- Kanban 方向；
- publication records；
- 一些旧的选题链路；
- 一些重复的数据结构；
- 一些不再成立的历史兼容路径。

删除并不意味着失败。

很多时候，删除意味着我们终于理解了产品真正需要什么。

一个系统的成熟，不只是功能增加，也包括：

> 知道哪些东西不再值得继续维护。

---

## 十四、接下来应该怎么走

如果继续推进，我认为最重要的不是再增加十个新模块，而是完成三件事。

### 第一，做一次真正的发布级稳定性验收

需要有一条全新的、干净的安装路径：

~~~text
复制 .env
→ docker compose up --build
→ API 就绪
→ Worker 就绪
→ Web 就绪
→ 采集
→ 生成草稿
→ 生成图片
→ 查看资产
→ 人工发布
~~~

这条链路必须在真实环境中完成，而不是只在当前开发机里成立。

### 第二，把技能运行时做成可信的执行层

后续 Skill 体系应该继续强化：

- 结构化目标；
- 工具 schema；
- reference 读取记录；
- 输出验证；
- save_draft 等关键动作证据；
- 幂等恢复；
- 可见失败；
- 人工确认点。

最终用户应该知道：

> 这个结果为什么被认为完成，哪些步骤已经完成，哪些步骤没有完成。

### 第三，控制新增产品线

数字人、文字视频、逐字稿独立产品、桌面客户端，都有价值。

但它们不应该同时成为最高优先级。

我更愿意先把核心闭环做稳：

~~~text
采集 → 甄选 → 创作 → 草稿 → 素材 → 人工发布
~~~

然后再判断：

- 文字视频是否真的成为高频工作流；
- 逐字稿是否值得独立成产品；
- 数字人是否有真实使用场景；
- 桌面客户端是否比当前自托管 Web 更简单。

## 结语：这个项目真正完成的，不是功能数量

如果只看 Git 提交，这个项目像是在不断加功能：

- 加采集源；
- 加 AI；
- 加 Agent；
- 加 Skill；
- 加任务；
- 加素材；
- 加视频；
- 加数字人；
- 加插件。

但如果从创始人的角度看，它真正经历的是几次认知变化。

第一次，我以为问题是“如何让 AI 帮我写更多内容”。

后来发现，问题是“如何把信息、素材、创作和发布连成一个闭环”。

第二次，我以为问题是“如何让多个 Agent 协作”。

后来发现，问题是“如何让一次内容生产可恢复、可解释、可审计”。

第三次，我以为问题是“如何把更多功能加进来”。

后来发现，问题是“哪些能力应该留下，哪些能力应该删掉”。

现在的 Ediora / 述策，仍然不是一个完成品。

它有很多成熟的部分，也有很多需要真实环境验证的部分；它还背负着一些历史代码、旧架构和未完全收敛的产品方向。

但它已经从一个“想做很多事情的 AI 内容项目”，逐渐变成了一个有清晰原则的内容基础设施：

- 采集和创作分离；
- 原始数据和派生数据分离；
- AI 生成和人工发布分离；
- job 状态持久化；
- 工具调用可审计；
- Skill 有执行边界；
- 资产有统一归属；
- 外部 provider 不被假设为永远可靠；
- 真实浏览器和真实数据优先于漂亮的单测；
- 产品边界优先于架构炫技。

这可能是到目前为止，项目最重要的成果。

不是我们已经做完了多少页面，而是我们终于越来越清楚：

> 一个真正可长期使用的 AI 内容产品，核心不在于让模型说得更多，而在于让每一步都能被看见、被验证、被恢复，并且最终把决定权交还给人。

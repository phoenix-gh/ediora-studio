# Ediora 用户使用文档设计

## 背景

Ediora 当前的根 `README.md` 同时承担产品介绍、开发启动、自托管部署、运行时配置和部分功能说明。仓库中还有自托管文档以及大量设计、实施计划，但缺少一套专门面向产品使用者、可以按实际任务连续阅读的使用文档。

本设计定义一套独立的 Markdown 用户文档。仓库只负责组织和维护 Markdown 源文件及少量必要截图；官网负责渲染、导航、主题和发布。

## 目标

- 让已经能够打开 Ediora 的使用者，通过一条推荐路径完成第一次内容创作。
- 以核心流程为首版重点，再为复杂或独立能力提供专题文档。
- 让每项操作都包含成功判断，使用户知道操作是否生效。
- 建立稳定、通用的 Markdown 结构，便于官网直接消费。
- 让文档内容能够随产品变化单独维护，避免继续扩张根 `README.md`。

## 非目标

- 不介绍开发环境、数据库、API、worker 或内部任务实现。
- 不重写 `docs/self-hosted.md` 中的部署和运维说明。
- 不负责官网的文档框架、页面样式、导航配置、搜索、渲染或发布。
- 不覆盖所有页面、按钮和高级选项。
- 不描述只存在于设计、计划或尚未核实的功能。

## 目标读者与首版成功标准

目标读者是已经完成安装、能够进入 Ediora，但不了解产品工作流的日常使用者。首版的核心成果是：用户从一个内容来源出发，经过筛选和创作任务，得到一篇已检查、可继续发布的完整草稿。

实际发布会因目标平台、账号权限和浏览器扩展而变化，不作为快速上手流程的必达终点。发布入口和前置条件可以在发布前准备章节中简要说明，具体平台流程以后以独立专题补充。

## 文档组织方式

文档采用“核心流程 + 独立专题”的混合结构：

```text
docs/user-guide/
├── README.md
├── quick-start.md
├── setup.md
├── collect-content.md
├── select-content.md
├── create-draft.md
├── edit-and-prepare.md
├── task-management.md
├── text-video.md
├── digital-human.md
├── troubleshooting.md
└── images/
    ├── quick-start-settings.png
    ├── quick-start-content-selection.png
    ├── quick-start-creation-task.png
    └── quick-start-draft-editor.png
```

文件名使用小写英文和连字符。文档之间使用相对链接，不依赖官网路由规则。

### `README.md`

说明 Ediora 解决的问题、文档适用范围、推荐阅读顺序和完整文档索引。它是用户文档入口，不承载详细操作步骤。

### `quick-start.md`

用一个连续案例完成首次内容创作。它只展示一条推荐路径，不枚举所有可选项。每一步都链接到对应的详细章节。

### `setup.md`

说明首次创作所需的最低配置，包括文字模型、图片模型、发布账号和必要数据源。高级模型参数和开发环境变量不进入本章。

### `collect-content.md`

说明如何添加信息源、触发采集，并确认内容已经进入系统。不逐个平台解释底层采集机制。

### `select-content.md`

说明如何浏览采集结果、判断创作价值，并把内容加入写作方案或创作流程。

### `create-draft.md`

说明如何手动创建任务、从线索创建任务、查看任务状态并找到生成结果。本章需要明确后台任务不会即时完成。

### `edit-and-prepare.md`

说明如何编辑草稿、关联素材、生成封面和正文配图，并完成发布前检查。实际发布只说明入口和前置条件。

### `task-management.md`

解释等待、运行中、成功、失败和取消等状态，以及查看日志、重试和避免重复提交的方法。可能产生重复模型调用或费用的操作必须明确提醒。

### `text-video.md` 与 `digital-human.md`

分别承载文字视频和数字人口播的进阶流程。两项能力不插入文章创作主线，避免首次使用路径分叉。

### `troubleshooting.md`

集中处理模型未配置、采集无结果、任务长时间未完成、素材不可用等跨功能问题。其他章节只保留短提示并链接到本章，避免重复维护。

## 单篇文档结构

除入口索引外，每篇操作文档尽量使用一致结构：

```markdown
# 文档标题

用两三句话说明这一功能适合解决什么问题。

## 完成后你将得到什么

## 开始前的准备

## 操作步骤

### 1. 打开目标页面

### 2. 完成具体操作

### 3. 确认操作结果

## 常见问题

## 下一步
```

章节可以按实际复杂度增减，但“操作步骤”必须同时说明用户动作和预期结果。

## Markdown 与语言规范

- 每个文件只使用一个一级标题。
- 界面路径使用粗体，例如：打开 **设置 → AI 模型**。
- 按钮和可见操作文字使用中文引号，例如：点击“保存配置”。
- 只使用用户能在界面中看到或容易理解的产品术语。
- 提示和警告使用通用引用块，不依赖框架专属组件：

  ```markdown
  > **提示：** 这项操作不会立即创建草稿。

  > **注意：** 重试可能再次产生模型调用费用。
  ```

- 使用标准 Markdown 标题、段落、列表、表格、代码块、相对链接和图片。
- 首版不添加官网框架专属 frontmatter、自定义组件或特殊容器语法。
- 不使用“稍后支持”“未来会有”等模糊承诺，只描述当前存在并核实过的行为。
- 敏感配置只说明保存位置和安全边界，不展示真实密钥、Cookie、Token 或用户数据。

## 截图策略

首版以文字为主，只为容易迷路的核心节点提供截图：首次配置、内容筛选、创作任务和草稿编辑。

- 截图必须来自实际运行界面，不使用示意图或占位图。
- 截图只保留理解操作所需区域，避免大面积展示无关界面。
- 图片必须使用描述性替代文本。
- 截图中不得出现密钥、Cookie、Token、私有账号信息或真实用户内容。
- 页面结构或关键按钮发生明显变化时，对应截图和步骤必须一起更新。
- 如果当前环境无法安全取得真实截图，相关图片引用不进入文档；文档应保持纯文字也能完整使用。

## 内容证据与核实方式

用户文档的事实来源按以下优先级核实：

1. 当前运行界面中的页面名称、按钮文字、状态和反馈。
2. 当前前端页面、组件和测试所表达的用户可见行为。
3. 当前后端接口和任务逻辑所表达的真实约束。
4. 根 `README.md` 与现有专项文档中的已实现边界。

`docs/superpowers/` 中的设计和计划只能帮助定位实现，不能单独作为“功能已存在”的证据。无法核实的外部服务行为应明确说明验证限制，不得写成已确认事实。

## 错误与异常说明

- 与当前步骤直接相关的错误，在步骤后给出简短处理方法。
- 跨功能或可能反复出现的问题统一放入 `troubleshooting.md`。
- 任务失败、取消、重试和重复扣费风险统一由 `task-management.md` 详细解释。
- 错误说明必须告诉用户下一步可以做什么，不能只复述错误信息。

## 维护约定

- 修改用户可见名称、核心操作路径、任务状态或安全边界时，同一变更应检查相关用户文档。
- 一个事实只在最合适的章节详细解释，其他章节通过相对链接引用。
- 快速上手只保留一条推荐路径；新增功能默认进入专题或详细章节，不扩张主线。
- 根 `README.md` 只增加用户手册入口，不复制整套使用说明。
- 官网将来需要元数据时，应另行定义稳定的内容契约，再统一添加 frontmatter，避免首版预设未知框架。

## 验收标准

- 新用户只阅读 `quick-start.md` 就能完成一次核心内容创作流程。
- 所有页面名称和按钮文字与当前产品一致。
- 每个操作步骤都包含预期结果或成功判断。
- 所有相对链接和实际存在的图片引用有效。
- 核心流程文档之间没有大段重复内容。
- 文档不包含开发、部署、数据库和内部任务实现细节。
- 文档不描述尚未实现或仅存在于计划中的能力。
- 图片不包含敏感信息，并且删除图片后仍不影响文字步骤的完整性。
- 根 `README.md` 提供清晰的用户手册入口。

## 首版实施顺序

1. 建立目录、入口索引和统一写作骨架。
2. 编写 `quick-start.md`，以它确定核心流程和跨章节链接。
3. 编写配置、采集、筛选、创作和编辑五篇主线文档。
4. 编写任务管理与故障排查。
5. 编写文字视频和数字人口播专题。
6. 在可运行且数据安全的环境中补充少量关键截图。
7. 检查链接、图片、标题层级、术语一致性和功能真实性。

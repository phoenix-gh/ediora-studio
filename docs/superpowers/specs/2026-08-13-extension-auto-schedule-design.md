# Chrome 插件自动填入发布时间设计

## 背景

述策 Chrome 插件已经能够检测 X 原生安排时间弹窗、恢复上次选择，并在用户点击 X 原生确认按钮后记录实际选择。连续安排多条内容时，用户仍需逐项修改下一次发布时间。

本功能在现有时间记忆上增加一个持久化复选框。启用后，每次打开 X 安排时间弹窗，插件自动填写“上次确认时间的下一小时”，并把分钟随机设置为 `00–15`。

## 已确认的产品规则

1. 工作台提供“自动填入发布时间”复选框。
2. 勾选状态持久保存；刷新 X 页面或重启浏览器后仍保持。
3. 每次 X 安排时间弹窗从关闭变为打开时，最多自动填写一次。
4. 有上次确认时间时，以它为基准；没有记录时，以当前本地时间为基准。
5. 基准时间的小时加 `1`，原分钟丢弃，分钟重新随机为闭区间 `00–15`。
6. 例如上次确认时间为 `10:47`，下一次自动填写为 `11:00–11:15`，不是 `11:47`。
7. 日期、月份、年份和 AM/PM 根据本地时间自然进位，包括午夜跨天、月末和年末。
8. 自动填写不会更新“上次安排”。只有用户点击 X 原生安排确认按钮后，弹窗中实际确认的时间才成为新的“上次安排”。
9. 同一个弹窗保持打开时不会重复随机。关闭后重新打开时重新计算；如果期间没有确认，仍以同一个旧基准计算，分钟可再次随机。
10. 取消勾选后保留当前旧行为：打开安排时间弹窗时恢复上次确认的原始时间，不做加一小时或随机分钟。

## 架构

### 时间与持久化

继续使用 X 页面 `localStorage`，与现有 `x_schedule_last_selection_v3` 保持同一所有权和生命周期。新增布尔键：

```text
x_schedule_auto_fill_enabled_v1
```

只有字符串 `true` 表示开启，其他值均按关闭处理。此设置不进入后端，也不通过草稿 API 或 service worker 传输。

`schedule-memory.js` 新增纯计算函数，根据已保存选择或当前 `Date` 计算下一次时间。函数接收可注入的随机数来源，使用 `Math.floor(random() * 16)` 得到 `0–15`，并输出现有标准 selection 结构。

### 弹窗生命周期

现有轮询已经使用 `wasOpen` 识别弹窗首次出现。首次出现后：

- 自动填时开启：计算并应用下一次时间，不保存；
- 自动填时关闭：执行现有恢复逻辑。

弹窗持续打开期间不再执行。弹窗关闭后 `wasOpen` 重置，下一次打开才重新触发。

现有 X 原生确认按钮监听保持唯一保存入口。自动写入产生的 `input` / `change` 事件不会直接写入 `localStorage`。

### 工作台界面

在头部“上次安排”信息附近增加原生复选框及文字“自动填入发布时间”。工作台初始化时从 `localStorage` 读取勾选状态；用户切换时立即持久化。

复选框只控制下次打开安排弹窗时的行为，不会立即寻找或修改当前已经打开的 X 弹窗，避免切换设置本身造成意外填表。

## 错误与边界

- 保存的上次时间无效时，按“没有记录”处理，使用当前本地时间。
- 随机函数产生异常范围值时限制到 `0–15`，不会生成无效分钟。
- `localStorage` 不可用时，复选框按关闭显示；切换不会抛出到 X 页面。
- 找不到完整的 X 日期/时间控件时沿用现有容错，不保存虚假的“上次安排”。
- 不自动点击 X 确认按钮，不自动发布，也不改变草稿状态。

## 验证

1. 单元测试覆盖：已有记录、首次使用、`00` 和 `15` 两端、午夜跨天、AM/PM、设置读写和存储异常。
2. 生命周期测试覆盖：开启时弹窗每次打开只填一次；关闭时走旧恢复逻辑；自动填写不推进上次时间；确认后才保存实际值。
3. Chromium 测试覆盖：复选框显示、切换后刷新仍保持、模拟 X 安排弹窗打开时填入预期日期和 `00–15` 分钟。
4. 插件全量 Node 测试、manifest JavaScript 语法检查和 `git diff --check` 通过。

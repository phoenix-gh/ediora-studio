# Chrome 插件草稿列表重新排序设计

## 目标

为 Chrome 插件的文章/草稿列表增加“重新排序”操作。点击后只在当前插件页面内存中随机打乱待发布草稿顺序；除非用户刷新列表，否则后续筛选、选择和发布都沿用这次打乱后的顺序。

## 行为边界

- 首次加载和手动刷新仍使用服务端返回的数据，并由现有逻辑按更新时间排序。
- “重新排序”使用 Fisher–Yates 算法打乱当前待发布草稿数组。
- 重新排序不改变 `selectedId`、搜索关键词、平台筛选或草稿内容。
- 搜索和平台筛选只从当前打乱后的数组生成可见列表，不重新排序。
- “发布并下一条”只从当前数组移除已发布草稿，并依据当前可见顺序选择下一条；不会重新读取或重新排序。
- API 设置保存触发的刷新视为刷新列表，恢复服务端默认顺序。
- 随机顺序不写入后端、`localStorage` 或 Chrome storage；页面刷新后自然恢复服务端顺序。

## 实现方案

### 状态层

在 `chrome-extension/content/workbench-state.js` 增加纯函数 `shuffleDrafts`（或等价命名）：

- 接收当前 workbench state；
- 创建并随机打乱 `state.drafts` 的副本；
- 保留其他状态字段和当前选择；
- 空数组和单元素数组保持稳定。

`applyDrafts` 保持现有服务端排序逻辑，不将随机顺序持久化。现有 `publishDraftAndSelectNext` 继续基于当前 `state.drafts` 工作，因此发布后保留剩余项目的当前顺序。

### UI 层

在工作台头部刷新按钮附近增加“重新排序”按钮，使用独立的 `data-action="shuffle"`，并在事件处理器中调用状态层函数后重新渲染。按钮在发布进行中沿用现有操作禁用规则，避免与发布状态并发修改列表。

### 测试

在 `chrome-extension/tests/workbench.test.js` 覆盖：

1. 重新排序改变数组顺序但保留全部草稿和选中项；
2. 过滤后使用打乱后的相对顺序；
3. 发布打乱列表中的项目后，剩余列表顺序不被重新按时间排序；
4. `applyDrafts` 刷新仍恢复服务端时间排序；
5. UI 源码包含重新排序按钮和事件绑定。

## 非目标

- 不修改服务端草稿顺序或草稿状态 API。
- 不增加排序方式选择、拖拽排序、顺序持久化或跨页面同步。
- 不改变“已发布”按钮的 API 行为。

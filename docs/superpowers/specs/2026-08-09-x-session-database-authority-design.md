# X Session 数据库权威设计

日期：2026-08-09

## 1. 背景与问题

X 账号配置当前将完整的 `auth_token` 和 `ct0` 写入当前运行环境的
`FEEDGRAB_DATA_DIR/x_<slot>.json`，数据库只保存槽位、名称和脱敏预览。
开发环境、宿主机和 Docker 环境切换时，数据库记录仍然存在，但新的
session 目录可能没有对应文件，导致订阅采集使用不完整的账号池。

## 2. 目标与边界

- 数据库中的账号 session 是唯一权威来源。
- 当前环境的 `x_<slot>.json` 和 `x_<slot>.disabled.json` 是 feedgrab
  使用的派生缓存，不作为权威数据。
- 完整凭据以服务端加密值保存在数据库中，不通过 API、前端、任务参数或
  日志暴露。
- 启动和每次 X 采集前，先将数据库中的账号状态同步到当前 session 目录；
  同步未完成时不启动 feedgrab 采集。
- 保留现有外部 session（如 `feedgrab login twitter` 生成的文件），不读取、
  覆盖或删除它们。

## 3. 数据与密钥

`x_credential_accounts` 新增 `session_ciphertext` 字段，保存一个加密后的
JSON payload：

```json
{"auth_token":"...","ct0":"..."}
```

使用 Fernet 加密。优先使用稳定的 `X_SESSION_KEY`；未配置时从现有
`WORKER_TOKEN` 派生密钥，保证本地开发和 Docker 只要共享同一环境密钥
即可恢复数据库 session。密钥变化时不尝试猜测或降级为明文，恢复失败应给出
明确的服务端错误。

现有数据库迁移保持 `session_ciphertext` 可为空，以兼容旧账号。服务启动时：

1. 有加密 session：解密并以数据库值同步文件。
2. 没有加密 session 但当前托管文件存在：读取文件并补录加密值。
3. 两者都没有或文件内容无效：标记账号为失败，并提示重新填写凭据。

## 4. 同步流程

新增一个账号 session 同步边界，负责：

- 读取所有数据库托管账号；
- 对启用账号生成 `x_<slot>.json`；
- 对停用账号生成 `x_<slot>.disabled.json`；
- 目录不存在时创建并设置 `0700`，文件设置 `0600`；
- 只在文件缺失、状态不符或内容与数据库不一致时写入；
- 写入采用现有原子替换和文件锁。

同步触发点：

- API 启动对账；
- 手动单订阅采集；
- 手动全量采集；
- 回溯采集；
- 定时 X 采集。

所有启用的托管账号必须同步成功后，才开始本轮 X 采集。若某个启用账号
无法恢复，当前轮次不调用 `grab_timeline` 或搜索接口，并记录脱敏错误；外部
session 仍可被 feedgrab 原有机制识别，但不能绕过数据库托管账号的同步失败。

## 5. 配置与测试行为

- 新建账号：先生成加密值并写入数据库，同时写入当前 session 文件；任一步失败
  都回滚另一侧。
- 修改凭据：数据库新加密值和文件更新保持现有补偿恢复语义。
- 启停账号：数据库状态优先，文件只同步为 active/disabled 状态。
- 手动测试账号：先执行同步，再读取当前文件进行 feedgrab 测试。
- 旧账号：首次启动从现有 session 文件补录；如果旧环境文件不存在，需要用户
  重新输入一次完整凭据。

## 6. 验证范围

后端回归测试覆盖：

- 加密/解密不泄露完整凭据；
- 数据库 session 缺失时从现有文件补录；
- 当前 session 文件缺失时从数据库恢复；
- 数据库状态覆盖本地 active/disabled 状态；
- 恢复失败时不会调用采集器；
- 手动、定时、全量和回溯入口都在采集前执行同步；
- 数据库迁移对现有 `x_credential_accounts` 可重复执行。

不修改 feedgrab 的账号轮换逻辑，也不改变外部 session 的兼容行为。
